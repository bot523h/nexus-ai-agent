2. Correctly handle libpq-style URL parameters.
3. Do not forward unsupported parameters as arbitrary "asyncpg.connect()" keyword arguments.
4. Translate supported TLS requirements into driver-supported options or an SSLContext.
5. Never silently weaken TLS.
6. Preserve correct hostname and certificate verification semantics.
7. Handle unsupported "channel_binding" requirements explicitly.
8. Do not silently discard a security requirement.
9. Ensure password URL encoding and special characters work.
10. Ensure sync and async connection paths have consistent security guarantees.
11. Support the canonical Neon connection string format.
12. Distinguish direct Neon connections from PgBouncer pooled connections.

- "channel_binding=require"

- PostgreSQL direct endpoint

- missing TLS configuration
- connection timeout
- DNS failure.


Use SQLAlchemy's actual dialect "create_connect_args()" to inspect the arguments passed to the DBAPI.

Prepared Statement requirements:

- Inspect asyncpg statement-cache configuration.

- Evaluate connection pool strategy.

Acceptance:

4. F-002 — MAKE POSTGRES RESTORE DATA-SAFE


Finding:
A failed PostgreSQL Restore can destroy pre-existing target data.


Files:


- "src/nexus_ai_agent/maintenance/backup.py"
- "src/nexus_ai_agent/maintenance/restore.py"
- "tests/unit/test_restore_drill.py"


Root problem:


"pg_dump --clean --if-exists" generates destructive DDL.


Current restore uses "psql -v ON_ERROR_STOP=1" without guaranteeing transaction-level atomicity.


Required architecture:


Prefer this recovery design:


"Verified Backup"
→ "Isolated Restore Target"
→ "Schema Validation"
→ "Data Integrity Validation"
→ "Independent Verification"
→ "Controlled Promotion"


Do not restore directly over a critical production database as the default recovery strategy.


Required protections:


1. Validate source and target database identities.
2. Reject source-target identity collision.
3. Never treat "--force" alone as sufficient production authorization.
4. Explicitly identify the target host, database and environment.
5. Require an independent confirmation mechanism for destructive production recovery.
6. Prefer a newly created disposable restore database.
7. Preserve the original target until the replacement is proven.
8. Define a safe cutover strategy.
9. Ensure failed restore does not silently leave a partially destroyed target.
10. Sanitize the error report.


Transaction safety:


Evaluate "psql --single-transaction" ("-1") with "ON_ERROR_STOP=1".


Prove that the complete generated NEXUS dump is compatible with transactional execution.


If full-dump transactional restoration is not safe or practical, use isolated restore plus promotion rather than claiming atomicity.


Do not simply add "-1" without testing the full dump format, including PostgreSQL 17 trailers and all generated SQL statements.


Mandatory destructive regression test:


1. Create a disposable PostgreSQL database.
2. Create a table containing a sentinel row.
3. Generate a restore artifact containing destructive DDL.
4. Inject a failure immediately after the first destructive statement.
5. Execute restore.
6. Verify that original data is still recoverable.
7. Verify the failed target is classified correctly.
8. Verify no "RESTORE_PROVEN" is emitted.


The test must turn RED if the protection is removed.


Never run this scenario on Neon Production.

۱۸. قرارداد پذیرش نهایی


اصلاح فقط زمانی کامل است که:


- هیچ مشکل تایید شده‌ای در P0 باقی نمانده است.
- تمام مسیرهای PostgreSQL در محیط عملیاتی بسته نمی‌شوند.
- هیچ جایگزین پنهان SQLite در مسیرهای تولید معتبر باقی نمی‌ماند.
- مدیریت URL در PostgreSQL برای درایورهای async و sync آزمایش شده صحیح است.
- الزامات TLS همچنان پابرجاست.
- یک Restore ناموفق نمی‌تواند هدف قبلی را بی‌سروصدا نابود کند.
- هیچ راز و رمزی در خروجی گزارش یا لاگ فاش نشده است.
- هیچ اثر موقت کنترل نشده‌ای باقی نمی‌ماند.
- اسکریپت‌های مخرب به طور صریح محصور شده‌اند.
- هر ادعای بازیابی با شواهد واقعی به دست آمده مطابقت دارد.
- تأیید طرحواره برنامه مؤثر است.
- شواهد قابل تکرار و وابسته به منبع هستند.
- CI مسیرهای بازیابی بحرانی را پوشش می‌دهد.
- تمام رگرسیون‌های مواد برطرف شده‌اند.
- محدودیت‌های ابری به صراحت گزارش شده‌اند.


وضعیت نهایی باید دقیقاً یکی از موارد زیر باشد:


"سخت شده اما کامل نیست"
"تأیید شده با محدودیت‌ها"
«مسدود شده»


از VERIFIED استفاده نکنید، مگر اینکه تمام مدارک مورد نیاز واقعاً وجود داشته باشد.


به یاد داشته باشید:


سبز CI ≠ بازیابی ایمن


آدرس اینترنتی معتبر ≠ اتصال معتبر


POSTGRES الزامی ≠ POSTGRES اجباری


پشتیبان ایجاد شده ≠ پشتیبان قابل بازیابی


بازگرداندن خروج ۰ ≠ صحت داده‌ها اثبات شده است


پست‌های محلی ≠ نئون تأیید شد


تکمیل پیاده‌سازی ≠ تأیید مستقل


مسئولیت شما ارائه یک اصلاح کامل، ایمن و قابل آزمایش در شاخه مجازتان است - نه دریافت یک ادغام سریع.


با حقیقت زنده شروع کنید. مالکیت را حفظ کنید. علل ریشه‌ای را برطرف کنید. هر ضمانتی را اثبات کنید. قبل از ادغام، توقف کنید.
