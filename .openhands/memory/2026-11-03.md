- Branch head progression: `3db8843e` (PR #308 pre-existing) → `574da675` (behavioral guard +
  `--isolated`) → `be93808b` (hermetic postcondition tests). Base == main `5ce9f7d3`.
- **Real CI failures found on `574da675` (run 41738614295)** — NOT caused by the install script:
  `test`, all three `python-parity`, and `trust-mutations` failed on
  `test_ci_torch_disk_budget.py::test_postcondition_fails_closed_on_missing_torch` + X5 baseline.
  ROOT CAUSE: the postcondition reads the *running interpreter's own* metadata and runs
  `sys.executable -m pip check` against it, so a test executed in the ambient env leaks the real
  `torch` (so "absent torch" is wrong) and a real broken closure (so the X5 baseline is not green
  in `trust-mutations`, which installs the project `--no-deps`).
- FIX: every postcondition assertion now runs on a throwaway `python -m venv` (module-level cached
  `_HERMETIC`), whose only distribution is `pip`. `planned=14 killed=14 survived=0 invalid=0` locally
  AND in CI.
- Lesson (reusable): **a subprocess test that shells out to `sys.executable` is not hermetic**; any
  `importlib.metadata` / `pip check` / `pip config` assertion must run on a fresh venv, else it
  silently measures the CI image. This is exactly the class of bug the mission calls "test that
  passes without executing the code under test".

  survived; now behavioral + killed), M3 `--isolated` needed (env `PIP_EXTRA_INDEX_URL` is consulted
  even with an explicit `--index-url`; verified pip 26.x), L1 PEP 503 name normalization,
  M4 dynamic workflow discovery, L3 parity==continuum matrix equality.
