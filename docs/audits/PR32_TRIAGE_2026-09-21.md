## 2. The one bug that justified opening PR#32 in the first place (still live on `main`)

`features/gamification.py::GamificationEngine.claim_daily` on `main` (402 L):

```python
with Session(engine) as session:          # ← engine A, connection held open
    ...
    session.add(xp)
    session.flush()                       # ← uncommitted INSERT still locks the row/page
    ...
    streak_info = GamificationEngine.update_streak(user_id, chat_id)   # ← engine B, second connection
```

`update_streak()` opens **its own** engine and session while the first session holds an
uncommitted `INSERT` on the very same `userxp` row. On SQLite this is a **write-write deadlock on a
user's first ever claim** (the row does not exist yet, so the second connection blocks on the
pending insert of the first). Secondary defects in the same method:

* `datetime` values read back from SQLite are **naive**, so `now - xp.last_daily` mixes aware and
  naive datetimes → `TypeError` on the second claim for rows written by an older process;
* the payload never reports `streak_broken`, `title`, `xp` or `remaining_minutes`, so the Telegram
  surface cannot render the reward truthfully;
* a brand-new user is created with `streak=1, last_daily=now` **and then** gets another
  `update_streak()` pass → the first claim silently double-counts the streak.

PR#32 fixes all four by running the whole reward in **one session** (`_as_utc()` for legacy naive
timestamps, explicit `streak_broken`, richer payload). `main` does **not** have this fix — verified
by blob comparison, not by inference.

## 4. Counter-factual check (what this session must NOT do)

1. **Do not port `bot/surface/{tools,games,referral,community}.py`.** They would race
   `bot/feature_handlers.py` for the same `/calc`, `/tr`, `/convert`, `/wordle`, `/poll`, `/quiz`,
   `/anon_start`, `/start` commands. Two handlers for one command is exactly the "dead code behind
   the live handler" defect the audit was opened to remove.
2. **Do not restore PR#32's `features/ai_memory.py`.** It predates the consent API; restoring it
   would regress P0-5 (LLM egress consent) that PR#34 landed.
3. **Do not re-land `features/tools.py`.** `main`'s `ReminderSystem` is the one `app.py` binds at
   startup (`bind()` / `restore_pending()`); PR#32's `bind_bot()` variant has no restore path and
   would silently drop reminders across restarts.
