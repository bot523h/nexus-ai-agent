# پروتکل کار چند-عاملی (NEXUS AI Agent)

نسخه ۱.۰ — ۲۰۲۶-۰۹-۲۱ · نسخه انگلیسی: `docs/MULTI_AGENT_PROTOCOL.md`
فایل‌های همراه: `AGENTS.md` (قرارداد ریشه)، `.agents/board.json` (وضعیت)، `scripts/agent_board.py` (ابزار خط فرمان)

## چرا این پروتکل وجود دارد؟

چند عامل هوش مصنوعی به‌طور همزمان روی این مخزن کار می‌کنند، اما هر کدام در یک
**Sandbox ایزوله‌ی جدا** (هر جلسه Arena کلون و شاخه‌ی `arena/*` خودش را دارد).
بین Sandboxها **هیچ فایل‌سیستم مشترکی وجود ندارد**؛ تنها کانال مشترک، خودِ مخزن
گیت است. پس وضعیت هماهنگی باید داخل مخزن زندگی کند و با `pull/commit/push`
منتقل شود.

این همان الگوی استاندارد تیم‌های چند-عاملی است (چند جلسه‌ی Claude Code روی
worktreeهای یک ریپو):

* **لایه‌ی ایزوله‌سازی:** یک شاخه به از هر عامل؛ هیچ فایل مشترکی تا لحظه‌ی merge وجود ندارد.
* **لایه‌ی هماهنگی:** تخته‌ی وظایف با «اجاره» (Claim = مالک + ناحیه‌ی انحصاری + TTL) و «دفتر موکول».
* **لایه‌ی داوری:** چک‌کننده‌ی همپوشانی مسیرها + قانون «یک مالک برای گیت‌های کیفیت».

## چرخه‌ی وظیفه

```
queued ──claim──▶ active (مالک + TTL + مسیرهای انحصاری)
                     │
        ┌────────────┼─────────────┐
     release      defer        انقضای TTL
        ▼            ▼             ▼
      done      deferred ──▶ دوباره queued (خودکار با gc)
                + یادداشت در deferred_log
```

* **claim:** قبل از کدنویسی، تخته را بکش (`pull`)، وظیفه را `active` کن،
  **فوراً** کامیت و پوش کن. ادعای پوش‌نشده وجود ندارد.
* **TTL / تصاحب مهریضه:** هر ادعا ۲۴ ساعت (قابل تنظیم) اعتبار دارد؛ `gc`
  ادعاهای منقضی را خودکار آزاد می‌کند. عاملِ در حال کار با تکرار `claim` حمایتش را تمدید می‌کند.
* **defer (متوقف‌شدن مؤدبانه):** یادداشت دائمی با قالب فارسیِ معیار ثبت می‌کند:
  «چون عامل دیگری روی این محدوده کار می‌کرد متوقف شدم؛ این کار پس از آزاد شدن
  ناحیه انجام خواهد شد تا فراموش نشود.» + شرط `resume_when`.
* **release:** کار تمام → `done` → ناحیه آزاد؛ اولین عاملی که بعدش `next` بزند
  مالک بعدی می‌شود — همین است که «ادامه‌ی خودکار کار پس از اتمام عامل قبلی» را رقم می‌زند.

## برنامه‌ی فعلی دو عامل

1. **عامل A** (`arena/01a0c316-nexus-ai-agent`): ادعای فعالِ `P0-security-batch`
   (احراز هویت سراسری، رفع نشت PII داشبورد، path traversal، فایل‌های پروتکل) —
   مالک گیت‌های کیفیت؛ مالک انحصاری `bot/handlers.py` تا merge.
2. **عامل B** (هر جلسه دیگر): وظیفه‌ی `feature-wiring-batch` را **فقط پس از
   merge شدن PR عامل A به main** شروع می‌کند. تا آن زمان وظیفه `queued` است و
   در `deferred_log` ثبت شده تا فراموش نشود.
3. `bot/handlers.py` در ناحیه‌های هر دو عامل «انحصاری» است — مالکِ اجاره‌ی فعال
   صاحب فایل است؛ عامل دیگر حتی یک ویرایش کوچک هم نباید بزند.

## مرجع فرمان‌ها

```bash
python scripts/agent_board.py show                                  # تخته + پاک‌سازی مهریضه
python scripts/agent_board.py next --branch BR                      # من چه کار کنم؟
python scripts/agent_board.py claim TASK --branch BR [--ttl 24] [--gates]
python scripts/agent_board.py release TASK --branch BR
python scripts/agent_board.py defer TASK --branch BR --fa "…" --resume-when "…"
python scripts/agent_board.py check --files "a.py,b.py" --branch BR # داور همپوشانی
```

`check` اگر فایل‌ها با ناحیه‌ی فعالِ عامل دیگر تلاقی داشته باشد کد خروج ۱ می‌دهد —
به‌عنوان pre-push hook یا گام CI قابل استفاده است.

## خرابی‌ها و جذب آن‌ها

| خرابی | جذب |
|---|---|
| دو عامل همزمان ادعا کنند | تداخل در پوش گیت آشکار می‌شود؛ `claimed_at` زودتر برنده است؛ بازنده `show` می‌زند و موکول می‌کند |
| عامل وسط کار بمیرد | پس از TTL، `gc` ناحیه را آزاد می‌کند؛ `scope` و `deferred_log` نیت را حفظ می‌کنند |
| عامل با کلون کهنه کار کند | `check` روی pull تازه قبل از پوش + داور CI |
| کسی تخته را نادیده بگیرد | رد در PR Review؛ `AGENTS.md` اولین سند اجباری برای هر عامل است |
